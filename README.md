# Customer 360 Lakehouse for Retail Banking

Customer 360 Lakehouse is a Docker-based data platform that unifies a retail bank's customer, account, card, CRM and transaction data into one analytics-ready layer. It powers customer segmentation (RFM), churn risk detection, cross-sell targeting and cohort retention analysis, served through Trino SQL, a Power BI report and a Streamlit dashboard.

**Main use case:** Marketing can pull a campaign list (for example, high-value customers without a credit card) with a single SQL query in seconds, instead of waiting days for a manual extract across separate systems.

> Graduation project — Data Engineering program. All data is synthetic and generated for demo purposes.

## 1. Business Context

In a typical retail bank, customer data is scattered across operational systems:

| System | Data | Technology |
|---|---|---|
| Core Banking | Customers, accounts, deposits, loans, account transactions | Oracle |
| Card Management | Debit/credit cards, card transactions | PostgreSQL |
| CRM | Customer interactions, campaigns | PostgreSQL |

Pain points this project addresses:

- **No self-service:** every campaign list requires a DBA to write cross-system JOINs, taking 2–3 days.
- **No change history:** updates to customer address or segment overwrite old values, so there is no audit trail.
- **Inconsistent KPIs:** each team calculates metrics such as "total deposits" differently.
- **Load on production:** reports run directly against Core Banking and slow down the transaction system.

## 2. Solution Overview

| Metric | Before | After |
|---|---|---|
| Time to get a campaign customer list | 2–3 days (DBA) | Seconds (self-service SQL on Trino) |
| Who runs the query | DBA | Marketing / Analysts |
| Customer change history | Not available | SCD Type 2 |
| KPI definitions | Different per team | 28 standardized KPIs in one mart |
| Impact on production DB | Direct queries | None (separate Lakehouse) |

## 3. Data Set

The demo data is synthetic and reproducible (`seed: 42`), covering 12 months of transactions (Jan–Dec 2025) with `cob_dt = 2025-12-31`.

| Source | Entity | Rows | Notes |
|---|---|---:|---|
| Oracle | Branches | 100 | Nationwide, grouped by region |
| Oracle | Products | 30 | CASA, savings, loans, cards |
| Oracle | Customers | 10,000 | 70% Retail / 25% Priority / 5% VIP |
| Oracle | Accounts | ~30,000 | ~3 accounts per customer |
| Oracle | Deposits | ~5,000 | Term deposits |
| Oracle | Loans | ~3,000 | — |
| Oracle | Account transactions | ~1,050,000 | 12 months |
| PostgreSQL | Cards | ~8,000 | Debit + credit |
| PostgreSQL | Card transactions | ~212,400 | 12 months |
| PostgreSQL | CRM interactions | ~10,000 | 12 months |

Credit card ownership is generated by segment (VIP 70%, Priority 50%, Retail 15%). This leaves a pool of roughly **1,400 Priority and VIP customers without a credit card**, the target group for the cross-sell demo.

The source layer includes synthetic PII (name, national ID, phone). Business users only see the masked sandbox tables.

## 4. Architecture

```text
 SOURCE SYSTEMS                 LAKEHOUSE (MinIO + Apache Iceberg)                     SERVING
┌──────────────────┐     ┌──────────┐    ┌───────────────┐    ┌──────────────────┐    ┌────────────────┐
│ Oracle XE 21c    │     │  BRONZE  │    │    SILVER     │    │       GOLD       │    │ Trino (SQL)    │
│ Core Banking (7) │──┐  │ raw copy │───▶│ clean + SCD2  │───▶│ Customer 360 +   │───▶│ Power BI       │
├──────────────────┤  ├─▶│ 10 tables│    │ 7 dims        │    │ segments +       │    │ Streamlit      │
│ PostgreSQL 15    │──┘  │          │    │ 3 facts       │    │ branch analytics │    │ (masked data)  │
│ Card + CRM (3)   │     └──────────┘    └───────────────┘    └──────────────────┘    └────────────────┘
└──────────────────┘            Compute: Apache Spark 3.5   ·   Orchestration: Apache Airflow (11 DAGs)
```

- **Bronze** — raw copy of the 10 source tables via Spark JDBC, partitioned by `cob_dt`. Large transaction tables load incrementally.
- **Silver** — cleaned and conformed data: SCD Type 2 for `dim_customer` and `dim_account`, SCD Type 1 for other dimensions, and 3 fact tables.
- **Gold** — `mart_customer_360` (1 row per customer, 28 KPIs), 4 summary tables, RFM / churn / cross-sell / campaign segments and a branch monthly summary.
- **Sandbox** — PII-masked copy of the Customer 360 mart for business users.

The ETL is **metadata-driven**: one generic Spark job per layer reads its logic from YAML files. Adding a new table means adding a YAML config, not new code.

## 5. Analytics Logic

### RFM segmentation

Each customer gets an R, F and M score from 1 to 5 using `NTILE(5)` over the last 90 days of activity. The total score (3–15) maps to 7 segments:

| Total score | Segment |
|---|---|
| ≥ 13 | Champions |
| 10–12 | Loyal Customers |
| 7–9 | Potential Loyalists |
| 6 | New Customers |
| 4–5 | At Risk |
| 2–3 | Hibernating |
| < 2 | Lost |

### Churn risk (rule-based)

Based on days since the last account or card transaction:

| Days since last transaction | Churn risk |
|---|---|
| > 90 (or no transaction) | High — flagged as churn candidate |
| 61–90 | Medium |
| 31–60 | Low |
| ≤ 30 | Active |

### Campaign targeting

Each customer is assigned one campaign type, in priority order:

1. **Retention** — churn candidate in the *At Risk* or *Hibernating* segment.
2. **Cross_Sell_CC** — no credit card and AUM bucket Affluent or higher.
3. **Cross_Sell** — missing another product (deposit, loan).
4. **Upsell** — *Champions* or *Loyal Customers*.
5. **Awareness** — everyone else.

### Cohort retention

Customers are grouped by registration month. Retention for each period = active customers in that period ÷ cohort size.

## 6. Business Output

A typical Marketing request becomes one self-service query on the masked sandbox:

```sql
-- Q4 credit card cross-sell: high-value, active HCM customers without a credit card
SELECT customer_id, full_name_masked, primary_branch_code,
       aum_total, rfm_segment, days_since_last_txn
FROM lakehouse.sandbox.mart_customer_360_masked
WHERE has_credit_card = 0
  AND aum_total > 100000000              -- deposits > 100M VND
  AND rfm_segment IN ('Champions', 'Loyal Customers')
  AND days_since_last_txn <= 30
  AND primary_branch_code LIKE 'HCM%'
ORDER BY aum_total DESC
LIMIT 1000;
```

Six ready-to-use business queries are in [`sql_templates/trino/`](sql_templates/trino/):

| # | Use case | Owner |
|---|---|---|
| 1 | Credit card cross-sell list | Marketing |
| 2 | High-value churn risk customers | Retention |
| 3 | RFM segment distribution | Analytics |
| 4 | AUM breakdown by branch | Branch management |
| 5 | Customer 360 profile lookup | Customer service |
| 6 | Product penetration by segment | Product |

## 8. Data Quality Findings

Issues found and fixed while validating the dashboards against the data:

| Issue | Root cause | Fix |
|---|---|---|
| Cohort Size measure always returned 10,000 | `ALL(fact_txn_account)` removed the Cohort Month filter | Removed the modifier and verified with a DAX query |
| Wrong relationships in the Power BI model | Auto-detect routed 8 Silver tables through `campaign_target` | Rebuilt a star schema with `dim_customer` as the hub |
| Streamlit showed only 2 of the RFM segments | Hard-coded 11-segment list did not match the real 7-segment logic | Aligned the list with `rfm_segment.yml` |
| EDA page always showed "no data" | Gender filter used `Male/Female` while source data uses `M/F` | Used the actual source values |
| Negative period numbers in cohort analysis | Transactions cover ~12 months, registrations span ~24 months | Identified and documented the data limitation |
| `city` column had only 3 values | Generator created city independently of branch | Traced to the data generator and documented it |

**Key observation:** cohort retention stays around 99–100% in most periods. Early cohorts lack data in their first periods because transactions only cover 12 months, so this is noted on the dashboard.

## 9. Implemented Scope

- 10 simulated source tables across Oracle and PostgreSQL.
- 30 Iceberg tables across Bronze, Silver and Gold (10 per layer).
- SCD Type 2 for customer and account history.
- Customer 360 mart with 28 KPIs, 1 row per customer.

- 11 Airflow DAGs with ETL-flag dependencies, plus weekly Iceberg maintenance.
- 6 business SQL templates, a Power BI report and a Streamlit dashboard.

## 12. Quick Start

Requirements: Docker Desktop (≥ 10 GB RAM allocated), Python 3.10+, and a SQL client such as DBeaver.

```bash
cd lakehouse_etl
docker compose -f docker/docker-compose.yml build
docker compose -f docker/docker-compose.yml up -d
cd data_generator && pip install -r requirements.txt && python run_sql_gen.py
```

Then trigger the Airflow DAGs in order: `implement_iceberg_table_dag` → `bronze_initial_dag` → `bronze_core_banking_dag` + `bronze_card_crm_dag` → `silver_all_dag` → `gold_mart360_dag` → `gold_segmentation_dag` → `ops_pii_masking_daily_dag`.

Full step-by-step instructions: [Howtorun.md](Howtorun.md) and [docs/how_to_run.md](docs/how_to_run.md).
